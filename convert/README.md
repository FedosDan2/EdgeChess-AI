# Конвертация YOLOv8: PyTorch → ONNX → RKNN

Пайплайн для **Linux x86_64, Python 3.10 и CPU**. Все этапы работают в одном
окружении `uv`: экспорт, сравнение с PyTorch, калибровка и проверка RKNN в симуляторе.
GPU, камера и Firefly для этих этапов не требуются.

## Установка

Нужны [uv](https://docs.astral.sh/uv/getting-started/installation/) и системные
библиотеки OpenCV. На Ubuntu 22.04:

```bash
sudo apt-get update
sudo apt-get install -y libgl1 libglib2.0-0 libgomp1
cd convert
uv sync --locked
uv run --locked python --version
uv pip check
```

`uv` выбирает Python 3.10 по `.python-version` (при необходимости скачивает его),
создаёт `.venv` и устанавливает точные версии из `uv.lock`. Активация venv не нужна.
Все команды далее выполняются из `convert/`.

Это самостоятельный uv-проект: корневой `pyproject.toml` не управляет его зависимостями.
`pyproject.toml` задаёт прямые зависимости, `uv.lock` фиксирует также транзитивные
зависимости и хеши дистрибутивов. Оба файла должны храниться в Git. При намеренном
обновлении зависимостей выполняют `uv lock`, затем повторяют проверки пайплайна.

Одна совместимая конфигурация для всех этапов: PyTorch 2.4.0 CPU, torchvision 0.19.0,
Ultralytics 8.3.161, RKNN Toolkit2 2.3.2, ONNX 1.16.1, ONNX Runtime 1.20.1,
NumPy 1.26.4, protobuf 4.25.4. PyTorch загружается из отдельного CPU-индекса.
Для RKNN закреплён официальный wheel CPython 3.10 / Linux x86_64: дистрибутивы
этого релиза публикуют разные метаданные зависимостей. Ограничения пакета не обходятся.
`dill` требуется для старого checkpoint Ultralytics 8.1.9.
`setuptools` предоставляет `pkg_resources`, который Toolkit2 импортирует во время работы.

## Скрипты и порядок запуска

| Файл | Что делает |
|---|---|
| `01_download_samples.py` | Скачивает небольшую выборку Kaggle поштучно и фиксирует происхождение файлов |
| `02_export_and_check.py` | Получает эталон PyTorch, экспортирует два ONNX-графа и проверяет их результаты |
| `03_prepare_calibration.py` | Делает letterbox для калибровочных изображений и записывает список для Toolkit2 |
| `04_build_rknn.py` | Собирает FP16 или INT8 и проверяет детекции в программном симуляторе |
| `06_check_postprocessing.py` | Независимо сравнивает preprocessing/NMS с Ultralytics |
| `common.py` | Общая обработка входов и выходов, рисование рамок и сравнение |
| `Dockerfile` | Необязательное Ubuntu-окружение с тем же uv-проектом и lock-файлом |

Нумерация сохранена для совместимости существующих команд; шаги 00 и 05 не нужны.
`data/`, `artifacts/`, `.venv` и кэши исключены из Git. Перенос файлов между
машинами и настройки SSH не являются частью пайплайна.

### 1. Скачать изображения

```bash
uv run --locked python 01_download_samples.py
```

Источник — [Chess Pieces Detection Image Dataset](https://www.kaggle.com/datasets/imtkaggleteam/chess-pieces-detection-image-dataset),
подпапка `Chess_pieces`, использованная в [исходном ноутбуке](https://www.kaggle.com/code/imtkaggleteam/real-time-chess-pieces-detection-with-yolov8).
На знакомых модели данных легче отделить ошибки конвертации от ошибок распознавания.

Скачиваются 20 разных изображений `test`, 100 изображений `train` для калибровки,
их разметка и описание датасета. Seed=42. Дубли одинаковых имён в разных папках
не считаются отдельными изображениями. `data/manifest.json` хранит выборку, пути
источников и SHA256. Повторный запуск использует скачанные файлы.

Только manifest определяет состав выборки: оставшиеся в кэше файлы других запусков
не добавляются автоматически. Проверяется отсутствие точных копий между тестом и
калибровкой; это не исключает все близкие/аугментированные копии исходного датасета.

### 2. Экспортировать ONNX и проверить его

```bash
uv run --locked python 02_export_and_check.py --weights ../YOLOv8s_test.pt
uv run --locked python 06_check_postprocessing.py
```

`--weights` может указывать на другой совместимый checkpoint YOLOv8 Detect.
Нужна трёхмасштабная detection-голова; скрипт не предназначен для всех версий YOLO.
Загружать `.pt` следует из доверенного источника: десериализация может выполнять код.

ONNX — вычислительный граф с весами и описанием входов/выходов. Экспорт переводит
операции PyTorch в этот формат без повторного обучения. ONNX Runtime исполняет
граф на CPU. Фиксируем batch=1, вход 640×640, float32, opset=12 и внешний NMS.
Opset — версия определений операций ONNX. Размер входа после экспорта не меняется.

Создаются:

- `artifacts/yolov8s.onnx`: обычный выход `[1,4+nc,8400]` — координаты xywh и оценки классов;
- `artifacts/yolov8s_split.onnx`: шесть выходов, пары логитов рамок и оценок классов
  для масштабов 8/16/32. Декодирование DFL и координат переносится на CPU, свёртки
  и веса сохраняются. Это упрощает граф для NPU и разделяет выходы при квантовании.

У тестового checkpoint 13 классов: 12 сочетаний «цвет × фигура» и отдельный `bishop`.
Имена берутся из весов. Для него обычный выход имеет форму `[1,17,8400]`, а split:

| Stride | Рамки | Оценки классов |
|---|---|---|
| 8 | `[1,64,80,80]` | `[1,13,80,80]` |
| 16 | `[1,64,40,40]` | `[1,13,40,40]` |
| 32 | `[1,64,20,20]` | `[1,13,20,20]` |

64 = четыре стороны × 16 интервалов DFL. Декодер применяет softmax по интервалам,
находит среднее расстояние до каждой стороны и переводит его в координаты.
Декодер обязательно должен соответствовать конкретному формату экспорта.

Проверяются структура ONNX, числовые выходы и итоговые детекции на всех тестовых
изображениях. Допуски: координаты atol=0.02 пикселя / rtol=1e-4; оценки классов
atol=2e-5 / rtol=1e-4. Все итоговые рамки должны совпасть по классу и IoU >=0.99,
без пропущенных/лишних детекций. Ошибка проверки даёт ненулевой код завершения.

`model.json` хранит контракт, версии и хеши; `pytorch_predictions.json` — эталон;
`onnx_comparison.json` — результаты сравнения. Изображения с рамками сохраняются
в `artifacts/pytorch/`, `onnx/` и `split_onnx/`.

### Препроцессинг и постпроцессинг

`preprocess` читает изображение через OpenCV, сохраняет пропорции при масштабировании,
добавляет поля цвета 114 до 640×640 (letterbox) и переводит BGR в RGB.
Для PyTorch/ONNX используются float32 `[1,3,640,640]` в диапазоне 0…1.
Для RKNN — uint8 `[1,640,640,3]` в диапазоне 0…255; деление на 255 задаётся
в `std_values` Toolkit2. Нормализация выполняется ровно один раз.

`decode_split` восстанавливает координаты, `postprocess` выбирает класс,
отбрасывает confidence <0.25, выполняет NMS отдельно по классам с IoU=0.7
и возвращает координаты исходного изображения. NMS удаляет перекрывающиеся дубли;
IoU — площадь пересечения рамок, делённая на площадь их объединения.
Определение клеток доски и FEN — отдельная задача.

`06_check_postprocessing.py` сравнивает эту обработку с независимой реализацией
Ultralytics на всей тестовой выборке и трёх неквадратных форматах изображения.
Это защищает от общей ошибки обработки, которая иначе могла бы присутствовать
одновременно во всех сравниваемых движках.

### 3. Подготовить калибровку

```bash
uv run --locked python 03_prepare_calibration.py
```

При INT8 вещественные значения приближённо отображаются на сетку целых чисел.
PTQ-калибровка оценивает диапазоны значений на примерах без повторного обучения.
Разметка для неё не нужна; нужны изображения, похожие на рабочие входы.

Скрипт сохраняет заранее подготовленные letterbox PNG 640×640 без потерь в
`data/calibration/`. Геометрия при калибровке и инференсе получается одинаковой.
Пути в `data/calibration.txt` отсчитываются от папки самого списка (`data/`),
например `calibration/example.png`. `calibration_manifest.json` фиксирует хеши.
Дополнительно проверяется отсутствие совпавших подготовленных пикселей с тестом.

### 4. Собрать FP16 и INT8

```bash
uv run --locked python 04_build_rknn.py --precision fp16
uv run --locked python 04_build_rknn.py --precision int8
```

Toolkit2 последовательно выполняет `config` (целевая платформа `rk3588`, нормализация),
`load_onnx`, `build`, `export_rknn`. INT8 включается через `do_quantization=True`
с калибровочным списком. FP16 обозначает сборку без INT8 для RK3588; это не гарантия
типа каждого вспомогательного оператора.

Далее `init_runtime()` без target запускает симулятор на CPU; `inference` обрабатывает
те же тестовые изображения. Симулятор использует построенный объект RKNN в памяти:
`load_rknn` готового файла не заменяет эту последовательность проверки на компьютере.

`artifacts/rknn_fp16/` и `artifacts/rknn_int8/` содержат `model.rknn`, `build.log`,
`comparison.json` и `images/`. Проверка требует >=95% согласованности с PyTorch
в обоих направлениях, при совпадении класса и IoU >=0.9. Порог — индикатор изменения
детектора при переносе, а не универсальный критерий качества. При провале изучают
отчёт и картинки; порог автоматически не снижается.

## Необязательный Docker

На Linux можно использовать контейнер Ubuntu 22.04 с тем же `uv.lock`.
Все Python-зависимости в образе устанавливает `uv sync --locked`.
Команды ниже выполняются из корня репозитория:

```bash
docker build -t edgechess-convert -f convert/Dockerfile convert
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  -v "$PWD:/work" edgechess-convert python 01_download_samples.py
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  -v "$PWD:/work" edgechess-convert python 02_export_and_check.py --weights ../YOLOv8s_test.pt
```

Остальные скрипты запускаются аналогично: меняется команда после имени образа.
Окружение образа находится в `/opt/venv` и не перекрывается примонтированной папкой
репозитория. При запуске `uv run --no-sync` использует уже собранное окружение,
не пытаясь изменять его от имени пользователя контейнера. После изменения
`pyproject.toml` или `uv.lock` образ нужно пересобрать.
Ограничения CPU/RAM задаются при запуске Docker под конкретный хост,
а не зашиваются в проект. Сеть нужна для загрузки зависимостей и изображений.

## Границы проверки

Совпадение с PyTorch показывает сохранение поведения, но не правильность предсказаний.
mAP по ручной разметке здесь не вычисляется. Для итоговой модели нужна отдельная
валидация на отложенном наборе ChessRender360 и на целевых изображениях.

Симулятор не подтверждает работу сохранённого `.rknn` на NPU, совместимость драйвера,
FPS, нагрев и расход памяти платы. Следующий этап — запуск на Firefly через RKNN Lite2
на тех же изображениях и замеры после прогрева. Для этого достаточно SSH, камера не нужна.

Результаты последнего проверенного запуска приведены в `RUN_REPORT.md`.
