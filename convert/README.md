# Перенос YOLOv8s: PyTorch → ONNX → RKNN

Это отдельный учебный пайплайн на **Python 3.10**. Веса `../YOLOv8s_test.pt`
используются как временная модель до появления модели команды. Обучение здесь не
выполняется. Веб-интерфейс, камера и Firefly для первых этапов не нужны.

Основная работа выполняется на Windows: загрузка небольшой выборки, PyTorch,
экспорт ONNX и численное сравнение. Linux-ноутбук нужен для RKNN Toolkit2.

## Что находится в папке

| Файл | Назначение |
|---|---|
| `00_setup_windows.ps1` | Создать изолированное окружение Python 3.10 и поставить CPU-зависимости |
| `01_download_samples.py` | Скачать отдельные изображения и разметку Kaggle, записать происхождение и хеши |
| `02_export_and_check.py` | Загрузить веса, экспортировать два ONNX-графа, сравнить их с PyTorch |
| `03_prepare_calibration.py` | Подготовить 100 изображений с тем же letterbox, что используется при инференсе |
| `04_build_rknn.py` | В Linux собрать FP16 или INT8 и проверить результат в симуляторе |
| `05_run_on_laptop.ps1` | Передать необходимые файлы по SSH, выполнить Docker-сборку и скачать результаты |
| `06_check_postprocessing.py` | Независимо сравнить наш preprocessing/NMS с реализацией Ultralytics |
| `common.py` | Общий preprocessing, декодирование YOLOv8, NMS, сравнение и рисование рамок |
| `Dockerfile`, `requirements-rknn.txt` | Окружение Ubuntu 22.04 / Python 3.10 / RKNN Toolkit2 2.3.2 |
| `requirements-local.txt` | Зафиксированные основные зависимости Windows |
| `RUN_REPORT.md` | Результаты реально выполненных проверок и ограничения |

Скачанные данные лежат в `data/`, модели, изображения и отчёты — в `artifacts/`.
Эти папки, `.venv`, локальный интерпретатор `.python`, кэш и архив передачи исключены
из Git. Скрипты не изменяют корневые `pyproject.toml`, `.python-version` и исходные веса.

## 0. Подготовить Python

Все команды Windows ниже выполняются из корня репозитория в PowerShell.
Нужен установленный `uv`. Скрипт при необходимости скачает Python 3.10 в `convert/.python`.

```powershell
./convert/00_setup_windows.ps1
./convert/.venv/Scripts/python.exe --version
```

Используются PyTorch 2.5.1 CPU, torchvision 0.20.1, Ultralytics 8.3.161,
ONNX 1.16.1, ONNX Runtime 1.20.1, NumPy 1.26.4 и OpenCV 4.10.0.
`dill` нужен для загрузки старого checkpoint, созданного Ultralytics 8.1.9.
Файл `.pt` загружаем только из известного источника: это не просто таблица чисел,
его десериализация может выполнять Python-код.

В контейнере используется PyTorch 2.4.0 CPU: Toolkit2 2.3.2 требует torch <=2.4.0.
Это нормально — на ноутбук передаётся уже проверенный ONNX, а исходный `.pt` там не нужен.
Для этой работы CUDA и встроенная графика не используются.

## 1. Скачать небольшую выборку

```powershell
./convert/.venv/Scripts/python.exe convert/01_download_samples.py
```

Источник: [Chess Pieces Detection Image Dataset](https://www.kaggle.com/datasets/imtkaggleteam/chess-pieces-detection-image-dataset),
подпапка `Chess_pieces`, использованная автором [ноутбука](https://www.kaggle.com/code/imtkaggleteam/real-time-chess-pieces-detection-with-yolov8).
Это не ChessRender360: сначала проверяем перенос на знакомом модели домене.

Скрипт получает список файлов и скачивает поштучно:

- 20 разных изображений из `test` для проверки переноса;
- 100 разных изображений из `train` для калибровки INT8;
- соответствующую YOLO-разметку, описание и YAML классов.

Используется seed=42. Копии одного имени в `test/` и `test/images/` не считаются
разными изображениями. `data/manifest.json` хранит выбранные пути и SHA256.
Именно manifest определяет выборку: старые файлы в кэше после изменения отбора
не добавляются к тесту автоматически. Повторный запуск использует скачанные файлы.

Скрипт проверяет пересечение хешей файлов train/test; шаг 03 дополнительно сравнивает
подготовленные пиксели. Это не доказательство отсутствия всех близких/аугментированных
копий в исходном датасете. Маленькая выборка предназначена для отладки переноса.

Проверенный checkpoint содержит **13 классов**, включая отдельный `bishop` без цвета
и 12 классов «цвет × фигура». Мы не переименовываем и не удаляем класс при конвертации.

## 2. Получить эталон и экспортировать ONNX

```powershell
./convert/.venv/Scripts/python.exe convert/02_export_and_check.py
```

Для другой совместимой YOLOv8 detection-модели можно указать `--weights путь.pt`.
Скрипт специально ограничен трёхмасштабной головой YOLOv8 Detect, а не всеми версиями YOLO.

**Экспорт** переводит операции и веса PyTorch в вычислительный граф ONNX.
Обучение не повторяется. ONNX — переносимое описание вычислений; ONNX Runtime —
программа, выполняющая эти вычисления на CPU.

Фиксируем batch=1, вход 640×640, float32, opset=12 и внешний NMS. Opset обозначает
версию определений операций ONNX. Фиксированный размер упрощает перенос в RKNN.
Предупреждение PyTorch TracerWarning об условии размера ожидаемо для такого экспорта:
полученные графы не предназначены для произвольного размера входа.

Создаются два графа:

1. `artifacts/yolov8s.onnx`: обычный выход `[1, 17, 8400]` — четыре координаты
   xywh и 13 оценок классов для каждого кандидата.
2. `artifacts/yolov8s_split.onnx`: шесть выходов — пара «логиты рамок / оценки
   классов» для каждого из трёх масштабов. На стороне CPU `decode_split` восстанавливает
   тот же обычный выход. Мы переносим декодирование DFL и координат из графа на CPU;
   свёртки и обученные веса остаются теми же. Это упрощает граф для NPU и разделяет
   выходы координат и классов при квантовании.

Контракт split-графа:

| Масштаб (stride) | Рамки: DFL-логиты | Оценки классов |
|---|---|---|
| 8 | `[1,64,80,80]` | `[1,13,80,80]` |
| 16 | `[1,64,40,40]` | `[1,13,40,40]` |
| 32 | `[1,64,20,20]` | `[1,13,20,20]` |

64 = 4 стороны × 16 интервалов DFL. Декодер применяет softmax по интервалам,
вычисляет среднее расстояние до стороны и переводит его в координаты изображения.
Готовый декодер другого экспорта нельзя подключать без проверки формы и смысла выходов.

На каждом тестовом изображении сравниваются оригинальный PyTorch и оба ONNX-графа.
Допуски для всех координат: atol=0.02 пикселя, rtol=1e-4; для всех оценок классов:
atol=2e-5, rtol=1e-4. Дополнительно все итоговые рамки должны совпасть по классу и
IoU >=0.99 без пропущенных/лишних детекций. При провале скрипт возвращает ненулевой код.

Результаты:

- `artifacts/model.json`: контракт модели, классы, версии библиотек и хеши;
- `artifacts/pytorch_predictions.json`: эталонные детекции;
- `artifacts/onnx_comparison.json`: численные отклонения и результат проверки;
- `artifacts/pytorch/`, `onnx/`, `split_onnx/`: изображения с рамками.

### Препроцессинг: что подаётся в сеть

`common.preprocess` читает изображение, уменьшает его с сохранением пропорций,
добавляет поля цвета 114 (letterbox) до 640×640 и переводит BGR OpenCV в RGB.

Для PyTorch/ONNX массив имеет формат `[1,3,640,640]`, float32 и значения 0…1.
Для RKNN передаём `[1,640,640,3]`, uint8 и значения 0…255. Деление на 255
выполняется настройкой `std_values` внутри RKNN. Второй раз делить на 255 нельзя.

### Постпроцессинг: что делаем с выходами

`decode_split` восстанавливает рамки из split-графа. `postprocess` выбирает наиболее
вероятный класс, оставляет confidence >=0.25, выполняет NMS отдельно для каждого
класса с порогом IoU=0.7, убирает letterbox-поля и возвращает координаты исходного
изображения. IoU — доля пересечения двух рамок относительно площади их объединения.
NMS удаляет сильно перекрывающиеся дубли одной детекции.

Это ещё не распознавание клеток и FEN: геометрия доски — следующий модуль проекта.

### Независимая проверка обработки

```powershell
./convert/.venv/Scripts/python.exe convert/06_check_postprocessing.py
```

Общий preprocessing/postprocessing мог бы одинаково ошибаться во всех движках.
Поэтому отдельный скрипт сравнивает его с LetterBox, NMS и восстановлением координат
из Ultralytics. Проверяются все тестовые изображения и три неквадратных формата.

## 3. Подготовить калибровку INT8

```powershell
./convert/.venv/Scripts/python.exe convert/03_prepare_calibration.py
```

Квантование отображает вещественные веса и промежуточные значения в ограниченную
сетку целых чисел. Это может уменьшить модель и ускорить NPU, но добавляет ошибку
округления. При PTQ обучение заново не выполняется: на калибровочных примерах
Toolkit2 оценивает диапазоны значений и выбирает параметры квантования.

Калибровочные изображения должны быть похожи на рабочие входы. Их разметка не нужна.
Тестовые изображения в калибровку не включаем.

Скрипт заранее делает тот же letterbox и сохраняет PNG 640×640 без потерь в
`data/calibration/`. Так Toolkit2 не заменит letterbox простым растяжением картинки.
`data/calibration.txt` содержит пути относительно собственной папки `data/`
(например, `calibration/example.png`), а `calibration_manifest.json` —
исходные пути и хеши. При чтении PNG Toolkit2 получает RGB.

## 4. Собрать и проверить RKNN на ноутбуке

```powershell
./convert/05_run_on_laptop.ps1
```

По умолчанию используется `LijnxArcher@192.168.3.11`; другой адрес задаётся
`-SshTarget user@host`. Нужен доступ по SSH и право запускать Docker.
Для повторения только INT8-сборки можно передать `-Precision int8`.
Рабочая папка ноутбука — `~/edgechess-convert/convert`. Скрипт передаёт архив
необходимых входов, собирает контейнер и запускает две независимые сборки.
Ограничения контейнера: 2 CPU, 5 GiB RAM, до 7 GiB RAM+swap. GPU, privileged и
права на системные файлы хоста не требуются. Первый Docker build скачивает зависимости.

Что выполняет `04_build_rknn.py`:

1. `config`: выбирает `rk3588` и нормализацию RGB /255.
2. `load_onnx`: загружает проверенный split-граф и проверяет его SHA256.
3. `build`: оптимизирует и компилирует граф; `do_quantization=False` для FP16,
   `True` с `calibration.txt` для INT8.
4. `export_rknn`: сохраняет модель под Rockchip.
5. `init_runtime()` без target: запускает программный симулятор на CPU ноутбука.
6. `inference`: прогоняет те же тестовые картинки, декодирует выходы и сравнивает
   детекции с эталоном PyTorch.

FP16 здесь — название сборки без INT8-квантования для RK3588, а не обещание,
что каждый вспомогательный оператор графа обязательно исполняется в FP16.

После экспорта сохраняем объект RKNN в памяти и используем его для симулятора.
Загрузка готового `.rknn` через `load_rknn` не заменяет эту последовательность
проверки на компьютере. `.rknn` затем отдельно проверяется на настоящей плате.

Для ручного запуска внутри уже подготовленной папки ноутбука:

```bash
cd ~/edgechess-convert
docker build -t edgechess-convert:py310 convert
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  --cpus=2 --memory=5g --memory-swap=7g \
  -v "$PWD/convert:/work/convert" edgechess-convert:py310 \
  04_build_rknn.py --precision fp16
# Затем повторить команду с --precision int8.
```

Получаем `artifacts/rknn_fp16/` и `artifacts/rknn_int8/`:

- `model.rknn` — модель;
- `build.log` — подробный журнал Toolkit2;
- `comparison.json` — размер, хеш, окружение, согласованность с PyTorch;
- `images/` — результат детекции.

Тест RKNN требует >=95% совпадений в обоих направлениях при совпадении класса и
IoU >=0.9. Пороги служат сигналом заметного изменения детектора при переносе;
это не универсальные требования к качеству. При провале изучаем рамки и лог,
не снижаем порог автоматически. JSON сохраняется и при провале проверки.

## Что результаты доказывают, а что ещё предстоит

Совпадение с PyTorch проверяет сохранение поведения модели после переноса.
Оно **не доказывает**, что сами предсказания верны. В данном пайплайне mAP по
разметке не вычисляется. Для итоговой модели нужна отдельная валидация на
репрезентативном отложенном наборе ChessRender360 и затем на целевых изображениях.

Симулятор не измеряет скорость NPU, реальное потребление памяти платы, нагрев и
совместимость установленного runtime/драйвера. Следующий аппаратный этап —
передать RKNN и тестовые изображения на Firefly, запустить через RKNN Lite2,
подтвердить результаты и отдельно измерить inference/preprocessing/postprocessing.
Для этого достаточно SSH; камера на этом этапе не обязательна.
