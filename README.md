# EdgeChess AI: NPU-powered Chess Assistant
## Документация

### 1. Название проекта
**EdgeChess AI: NPU-powered Chess Assistant** (Автономный шахматный помощник/противник на базе Edge AI).

### 3. Какую задачу решает проект
Проект решает задачу создания автономной Edge AI-системы, которая в реальном времени анализирует шахматную партию (как на физической доске, так и на экране монитора в формате chess.com). Система распознает текущее состояние доски, фиксирует ход игрока, вычисляет оптимальный ответный ход с помощью шахматного движка и озвучивает рекомендацию через динамик, имитируя игру с живым соперником или выступая в роли ассистента.

### 4. Какую нейронную сеть планируется использовать
Архитектура **YOLOv8n** (или YOLOv11n) для задачи Object Detection (детекция объектов на изображении).

### 5. Почему выбрана именно эта сеть
YOLOv8/v11 обеспечивает оптимальный баланс между точностью (mAP) и скоростью инференса, что критично для работы в реальном времени на NPU RK3588S. Данная архитектура имеет нативную поддержку в RKNN Toolkit2, позволяет эффективное INT8-квантование с минимальной потерей точности и легко кастомизируется под специфичный набор классов.

### 6. На каких данных она будет обучаться
Будет использован **смешанный датасет** для обеспечения инвариантности модели к цвету фигур и типу доски:
*   **База:** Открытый датасет "Chess Pieces" (Roboflow Universe) с готовой разметкой bounding box.
https://universe.roboflow.com/joseph-nelson/chess-pieces-new/browse?queryText=&pageSize=50&startingIndex=0&browseQuery=true
*   **Собственный сбор:** ~100–150 фотографий физической доски под углом ~45° (имитация камеры на уровне глаз) + ~100 скриншотов/фото монитора с chess.com (с разными цветовыми темами).
*   **Классы (8 штук):** `pawn`, `rook`, `knight`, `bishop`, `queen`, `king`, `chessboard`, `hand`.
*   **Уникальная логика определения цвета:** Цвет фигуры (белая/черная) не является отдельным классом сети. Он определяется на этапе пост-процессинга исключительно **анализом яркости пикселей (HSV Value)** внутри bounding box. Это делает модель универсальной для любых тем оформления.
*   **Обработка окклюзии:** Класс `hand` решает проблему перекрытия фигур рукой игрока во время хода. Однако при угле камеры ~45° в кадре также видны руки противника, находящиеся **за** доской. Наивный пропуск всех кадров с детекцией `hand` привёл бы к потере большинства валидных кадров.

**Решение — пространственная фильтрация через IoU с bounding box доски:**

1. На каждом кадре детектируются все объекты: фигуры, `chessboard`, `hand`.
2. Bounding box класса `chessboard` используется как **зона интереса (ROI)**.
3. Для каждого обнаруженного `hand` вычисляется **IoU** (Intersection over Union) с bbox `chessboard`.
4. **Если IoU(hand, chessboard) > 0.15** — рука перекрывает доску (игрок делает ход). Кадр **пропускается**.
5. **Если IoU(hand, chessboard) ≤ 0.15** — рука находится за пределами доски (противник, зритель). Кадр **валидный**, рука игнорируется при построении матрицы 8x8.
6. **Если `hand` не обнаружен** — кадр **валидный**.

Данный подход не требует дополнительных классов или дообучения мод

### 7. Какая периферия будет подключена к Firefly
1. **USB или CSI видеокамера** (для захвата изображения доски в реальном времени).
2. **Динамик** (3.5mm jack или USB, для аудио-вывода).

### 8. Как нейронная сеть будет взаимодействовать с этой периферией
1. **Камера → NPU:** Приложение захватывает кадры с камеры (3–5 FPS). Если детектор видит класс `hand`, кадр пропускается. Если виден `chessboard`, применяется алгоритм Perspective Transform для виртуального выравнивания доски (вид строго сверху). Выпрямленный кадр подается на NPU для инференса YOLO.
2. **Логика → Динамик:** Координаты обнаруженных фигур преобразуются в матрицу 8x8. Цвет фигуры определяется по HSV-яркости. Данные собираются в стандартную FEN-строку. При изменении FEN-строки (зафиксирован ход) CPU запускает шахматный движок (Stockfish) для расчета лучшего ответа. Текстовое описание хода передается в легкий оффлайн TTS-движок (Piper TTS), который генерирует аудиопоток и выводит его на подключенный динамик.

## Распределение обязанностей (Роли в команде)

Для обеспечения полного цикла разработки Edge AI-системы обязанности распределены по следующим функциональным ролям. Каждый участник отвечает за свой модуль, но все компоненты интегрируются в единое приложение.

### 🎯 1. Lead Data & CV Engineer (Инженер по данным и компьютерному зрению)
*   Сбор и подготовка смешанного датасета (физическая доска + цифровые скриншоты).
*   Разметка данных (Roboflow/CVAT): 6 классов фигур, `chessboard`, `hand`.
*   Обучение модели YOLOv8/v11 (PyTorch), подбор гиперпараметров.
*   Валидация качества модели (mAP, Precision, Recall).
*   Экспорт обученной модели в формат **ONNX**.

### ⚙️ 2. NPU & Optimization Engineer (Инженер по оптимизации и NPU)
*   Конвертация ONNX → **RKNN** с использованием RKNN Toolkit2.
*   Настройка препроцессинга и постпроцессинга для NPU.
*   INT8-квантование модели (подготовка calibration dataset).
*   Написание скрипта инференса на Python/C++ для Firefly RK3588S.
*   Замер производительности: время инференса (мс), FPS, размер модели, сравнение PyTorch vs RKNN.

### 🧠 3. Logic & Audio Engineer (Инженер по логике и аудио)
*   Разработка алгоритма построения матрицы 8x8 из координат YOLO.
*   Реализация определения цвета фигур через анализ яркости пикселей (HSV Value) внутри bounding box.
*   Генерация и парсинг **FEN-строк** (Forsyth-Edwards Notation).
*   Интеграция шахматного движка **Stockfish** (через `python-chess`) для расчета лучшего хода.
*   Настройка и интеграция оффлайн TTS-движка **Piper** для озвучивания хода через динамик.

### 🔗 4. System Integration & DevOps (Инженер по системной интеграции)
*   Настройка окружения на Firefly RK3588S (драйверы NPU, зависимости).
*   Реализация пайплайна захвата видео с камеры (OpenCV, 3-5 FPS).
*   Разработка алгоритма **Perspective Transform** (Homography) для виртуального выравнивания доски по классу `chessboard`.

*   Сборка единого приложения, написание `README.md`, подготовка сценария итоговой демонстрации.

## 🔄 Архитектура пайплайна и взаимодействие модулей

1. **Capture (System Integration)**: Камера захватывает кадр. Если детектор видит `hand`, кадр пропускается.
2. **Preprocessing (System Integration)**: Находится `chessboard`, применяется Perspective Transform для получения вида строго сверху.
3. **Inference (NPU Optimization)**: Выпрямленный кадр подается на NPU RK3588S. Модель YOLO возвращает bounding box'ы фигур.
4. **Logic (Logic & Audio)**: Координаты bbox преобразуются в сетку 8x8. Цвет фигуры определяется по HSV-яркости. Формируется FEN-строка. Если FEN изменился, Stockfish рассчитывает ход.
5. **Output (Logic & Audio / NPU Optimization)**: Текстовый ход передается в Piper TTS, аудиопоток выводится на динамик. Метрики инференса логируются.
