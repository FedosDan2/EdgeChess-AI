# Виртуальная камера EdgeChess

Интерактивная 3D-доска отправляет JPEG-кадры в ONNX Runtime на Linux CPU.
Пользователь делает ходы за обе стороны; движка нет. Результаты модели рисуются
поверх сцены: bbox, класс, confidence. Рамки сохраняются между ответами, **в том
числе при движении камеры**, поэтому некоторое запаздывание ожидаемо.

Это самостоятельная среда **Python 3.10 + uv**. Ей не нужны PyTorch и RKNN Toolkit.
Frontend собирается отдельно через Node.js и npm; uv управляет Python-зависимостями.
Поддерживаемая серверная платформа первой версии — Linux x86_64.

## Запуск

Понадобятся uv, Node.js 22 LTS и npm. Сначала выполните шаг 02 из
[конвертационного пайплайна](../convert/README.md): сервер использует
`convert/artifacts/yolov8s.onnx` и соответствующий `model.json`.
Хеш ONNX проверяется при старте, чтобы не смешивать веса и список классов.

Из корня репозитория:

```bash
cd web
uv sync --locked
cd frontend
npm ci
npm run build
cd ..
uv run --locked uvicorn backend.app:app \
  --host 127.0.0.1 --port 8000 \
  --ws-max-size 2097152 --ws-max-queue 1
```

Откройте `http://127.0.0.1:8000`. Один сервер отдаёт страницу, API и WebSocket;
отдельный frontend-сервер для обычного запуска не требуется. При старте модель
делает пять прогревочных проходов, после чего доступен поток.

Если сервер на другом Linux-компьютере, в отдельном терминале на компьютере с
браузером поднимите туннель (подставьте своё имя пользователя и адрес):

```bash
ssh -N -L 8000:127.0.0.1:8000 user@linux-host
```

После этого открывается тот же локальный адрес. Приложение рассчитано на локальную
работу через SSH и один активный поток; публичная публикация не настроена.

По умолчанию ONNX Runtime использует четыре CPU-потока. Настройка перед запуском:

```bash
export EDGECHESS_THREADS=4
# Необязательные пути к другой паре артефактов стандартного экспорта YOLOv8:
export EDGECHESS_MODEL=/absolute/path/yolov8s.onnx
export EDGECHESS_METADATA=/absolute/path/model.json
```

Число потоков влияет на измерения: сравнивайте модели с одинаковыми настройками.
RKNN здесь пока не запускается. Для будущего NPU-бэкенда можно сохранить контракт
`Detector.predict()` и заменить реализацию инференса.

## Управление

- Нажмите фигуру, затем клетку назначения. Разрешённые клетки отмечены точками.
  Соблюдаются очередь ходов, шах, рокировка, взятие на проходе и превращение пешки.
  Тип превращения выбирается рядом с FEN.
- Введите FEN и нажмите «Применить» или Enter. Ошибочная запись не меняет доску.
  «Начальная позиция» восстанавливает исходную расстановку.
- Тяните мышью для вращения камеры, используйте колесо для масштаба.
  «Ракурс» возвращает начальную камеру.
- «Рамки и классы» отключает только overlay: поток и измерения продолжаются.
- Частота виртуальной камеры ограничивается 10/15/30/60 FPS. Значение 30 FPS
  является целевым максимумом, а не гарантией браузера или сети.
- JSON и CSV сохраняют измерения за последние пять минут текущего подключения.
  JSON дополнительно содержит модель, её хеш, настройки и счётчики. CSV содержит
  только числовые измерения по кадрам. При переподключении начинается новая сессия.

Фигуры — собственная процедурная геометрия Three.js, с постоянным светом и
материалами. Это объёмная сцена, но она **не воспроизводит в точности ассеты
ChessRender360**. Для тестирования обобщения финальной модели набор геометрии нужно
сопоставить с её обучающими данными. Предсказания текущих весов не корректируются
по известной расстановке: неверные классы и пропущенные фигуры видны как есть.
Автоматического сравнения с FEN в этой версии нет.

## Как проходит кадр

1. `scene.ts` отрисовывает сцену независимо от модели через `requestAnimationFrame`.
   Для захвата берётся только 3D-canvas; рамки, интерфейс и подсказки ходов в кадр
   не попадают. Размер кадра 960×720, соотношение сторон сцены 4:3.
2. `encoder.ts` в Web Worker масштабирует снимок через OffscreenCanvas и кодирует
   JPEG с качеством 0.88. Пока кодирование занято, новый захват пропускается.
3. `main.ts` передаёт бинарное сообщение: **8 байт uint64 big-endian frame id,
   затем JPEG**. Время захвата остаётся в браузере. Размер сообщения ограничен 2 МиБ.
4. Сервер подтверждает приём сообщением `ack`. Клиент не отправляет следующий
   кадр до ACK и проверяет `bufferedAmount`, поэтому данные не накапливаются
   бесконтрольно в транспортном буфере. ACK не означает завершение инференса:
   передача следующего кадра перекрывается с обработкой текущего.
5. `app.py` держит один обрабатываемый кадр и максимум один ожидающий. Новый
   кадр заменяет ожидающий; счётчик `replaced` показывает эти замены.
6. Единственный worker выполняет JPEG decode, letterbox, ONNX и NMS вне цикла
   событий API. Сам ONNX Runtime использует заданное количество CPU-потоков.
7. Сервер возвращает `result` с тем же id, bbox в координатах исходного JPEG,
   классами, confidence, длительностями и счётчиками. Браузер масштабирует bbox
   в CSS-координаты overlay. Прозрачный canvas имеет `pointer-events: none`.

Препроцессинг и постпроцессинг берутся из `convert/common.py`: letterbox до
640×640, паддинг 114, BGR→RGB, NCHW float32 /255, class-aware NMS, confidence 0.25,
IoU 0.7 и обратное преобразование координат. Веб-версия использует **стандартный
ONNX**, с декодированными выходами `[1, 4+nc, 8400]`; split-head граф предназначен
для RKNN-пайплайна и сюда напрямую не подставляется.

Рамки остаются до следующего результата; движение сцены их не сбрасывает.
Пустой результат очищает рамки. Если ответа нет две секунды, устаревшие рамки
исчезают, интерфейс сообщает об ожидании. При потере соединения выполняется
повторное подключение каждые две секунды. Отсутствие ACK пять секунд закрывает
зависшее соединение. Второй одновременный клиент получает статус занятости.
Перед приёмом нового клиента сервер дожидается завершения нативного инференса
старого, даже если тот отключился в середине обработки.

## Что означают метрики

Все p50/p95 и обработанные FPS на экране относятся к последним пяти секундам.
Первые пять прогревочных проходов в них не входят.

| Метрика | Границы измерения |
|---|---|
| Инференс | Только `session.run()`, часы сервера `perf_counter()` |
| Подготовка | Чтение JPEG, decode, letterbox, нормализация |
| NMS | Отбор классов, suppression и восстановление bbox |
| Ожидание | От приёма кадра до фактического начала работы worker |
| Возраст | От начала снимка до получения результата браузером, одни часы `performance.now()` |
| Обработано FPS | Количество пришедших результатов / длительность окна |
| Отрисовка / захват | Реальные вызовы отрисовки и начало снимков в браузере |
| Заменено сервером | Принятые кадры, заменённые более свежими до начала обработки |
| Пропущено до отправки | Захваты, пропущенные из-за занятого кодировщика или транспорта |

Возраст включает кодирование, передачу в обе стороны, очередь и обработку,
но не ожидание следующей отрисовки overlay. Это **не чистый сетевой RTT**.
Счётчик пропусков не включает пропущенные браузером тики `requestAnimationFrame`.
В фоновой вкладке захват приостанавливается; измеряйте в активной вкладке.
Время браузера не вычитается из времени сервера: синхронизация часов не нужна.

### Отдельный бенчмарк модели

Остановите поток (закройте страницу), чтобы не конкурировать за CPU. Из `web/`:

```bash
uv run --locked python -m backend.benchmark \
  ../convert/data/test/images/*.jpg --runs 100 --output benchmark.json
```

Можно передать один файл или несколько изображений любого читаемого OpenCV
формата. Скрипт загружает и подготавливает их **до** измерений, прогревает модель,
затем измеряет только `session.run()` на batch=1. В JSON сохраняются отдельные
длительности, среднее, p50, p95, конфигурация и хеш модели. `model_only_fps` —
1000 / средняя задержка, а не FPS всей системы. Для скорости полной системы
используйте поток и его экспорт метрик.

## Скрипты и проверки

| Файл | Назначение |
|---|---|
| `backend/app.py` | FastAPI, WebSocket-протокол, ограничение очереди, жизненный цикл worker |
| `backend/inference.py` | Проверка артефактов, прогрев, ONNX CPU, измерение стадий |
| `backend/benchmark.py` | Изолированный бенчмарк модели |
| `frontend/src/scene.ts` | Доска, объёмные фигуры, камера, правила ходов |
| `frontend/src/encoder.ts` | Кодирование JPEG в отдельном Web Worker |
| `frontend/src/main.ts` | Поток, ACK/backpressure, overlay, метрики, экспорт |
| `frontend/src/metrics.mjs` | Процентили и масштабирование bbox |

Из `web/`:

```bash
uv run --locked pytest -q
cd frontend
npm test
npm run build
```

Python-тесты проверяют ограниченную очередь, перекрытие передачи и обработки,
переподключение, отказ второму клиенту, некорректные пакеты, letterbox и настоящий
ONNX. Только тест реальной модели пропускается, если артефактов ещё нет.
Frontend-тесты проверяют расчёты метрик, координаты bbox и шахматные операции.
Ручная браузерная проверка нужна дополнительно для камеры, canvas и Web Worker.

Для разработки можно запустить `npm run dev` в `web/frontend/`, оставив API
на порту 8000. Vite проксирует `/api` и WebSocket. Для обычных замеров предпочтительна
сборка `npm run build`, которую отдаёт FastAPI.
